Multi-Level Nested (N2+) Search — mustang-nested-testkit Results

Branch: shreanu/nested-poc-search-rewrite
Feature under test: multi-level (2 through 7 deep) dotted nested-path query support, INCLUDING Lucene delegation/acceleration for keyword-equality leaves at any depth — both bare single-conjunct equalities (e.g. products.variants.color = "red" alone) and compound predicates (equality AND-ed with a range/other clause, via the child-grain split).
Engine path: ExprTreeBuilder descends through each nested-array boundary, wrapping the leaf comparison in one {"nested":"<hop>","inner":...} JSON layer per boundary crossed, evaluated by the NESTED_ANY_MATCH_EXPR Rust UDF. A single-conjunct equality leaf (at any depth) is now recognized by NestedAnyMatchExprSerializer.canServe and served as a native NestedQueryBuilder chain; a compound predicate's equality conjunct is routed to Lucene at CHILD-element grain via NESTED_ANY_MATCH_CHILD, intersecting with the range/other clause at the SAME element before the ∃ roll-up.

What's new since the previous report: Lucene delegation now fires for multi-level keyword-equality predicates — both bare single-conjunct AND compound — not just DataFusion-only evaluation. Every case below shows the ACTUAL routing observed live (backends=[...]), so you can see exactly which predicates are now Lucene-viable that weren't before.
Two independent datasets, two independent depths:
  1. c3 (from the corpus, nqx_corpus.jsonl) — 3 levels deep (products → variants → specs), 15 cases, golden results pre-recorded from vanilla. Result: 14/15 correct, 9/15 now Lucene-viable (vs. 1/15 before this session's Lucene-delegation work).
  2. poc_deep7 (test-kit dataset, golden results captured live against a running vanilla OpenSearch node for this report) — 7 levels deep, depths 2 through 7, plus a compound-AND, an EXISTS, and a cross-branch case. Result: 10/10 correct, 7/10 now Lucene-viable.
Combined: 24/25 passed (96%), 16/25 now Lucene-viable — the single correctness miss (in the c3 set) is a pre-existing, documented negation-scoping ambiguity, unrelated to the Lucene-delegation work.

Not a regression. This is the ¬∃ (must_not) reading of a raw PPL not(nested) negation, which is genuinely ambiguous at the language level: vanilla OpenSearch's must_not(nested(...)) means “no element anywhere satisfies the inner predicate” (¬∃), while mustang evaluates the per-element boolean and negates it elementwise before rolling up existentially (∃¬: “some element fails the predicate”). Both are defensible readings of the same PPL text; the corpus records both as separate case IDs (this one is the ¬∃ reading) and its sibling f6_013 (the ∃¬ reading) matches exactly. This is the same, previously-documented ambiguity that already exists for the single-level cmts/cmts2 negation cases (family F3_neg_grain) — unrelated to the Lucene-delegation work in this report.
